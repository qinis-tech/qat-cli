# Code Standards

|                 |                                       |
| --------------- | ------------------------------------- |
| **Status**      | Normative                             |
| **Applies to**  | `src/`, `tests/`, configuration files |
| **Tools**       | ESLint 10 (flat config), Prettier 3   |
| **Enforced by** | `npm run verify`, CI                  |

ESLint owns **correctness**. Prettier owns **formatting**. Neither tool has an opinion
in the other's domain, and `eslint-config-prettier` is applied last to guarantee that.

## 1. Commands

| Command                | Purpose                                |
| ---------------------- | -------------------------------------- |
| `npm run lint`         | Lint the whole repository              |
| `npm run lint:fix`     | Lint and apply autofixes               |
| `npm run format`       | Format the whole repository in place   |
| `npm run format:check` | Verify formatting without writing (CI) |
| `npm run verify`       | format:check → lint → typecheck → test |

`verify` is the definition of a green build. Run it before every pull request.

## 2. Scope and exclusions

Linted and formatted: `src/`, `tests/`, `*.config.ts`, `eslint.config.js`.

Excluded from both, and why:

| Path                | Reason                                                         |
| ------------------- | -------------------------------------------------------------- |
| `dist/`             | Generated by `tsc`                                             |
| `node_modules/`     | Third-party code                                               |
| `coverage/`         | Generated by Vitest                                            |
| `.qat/`             | Local execution artefacts and reports                          |
| `tests/fixtures/`   | Self-contained Cypress projects written to Cypress conventions |
| `examples/`         | Deliberately representative of external projects               |
| `CHANGELOG.md`      | Generated by semantic-release                                  |
| `package-lock.json` | Generated by npm                                               |

Formatting must never be applied to `tests/fixtures/` or `examples/`. Those files exist
to test QAT against code it does not own, and reformatting them silently changes the
fixture's meaning.

## 3. Severity policy

| Level   | Meaning                             | Blocks merge                |
| ------- | ----------------------------------- | --------------------------- |
| `error` | Violates a decided standard         | Yes — ESLint exits non-zero |
| `warn`  | Advisory; action depends on context | No                          |

Rules are set to `error` unless the correct response genuinely depends on judgement.
The `warn` set is deliberately small:

| Rule                                       | Why it is a warning                                               |
| ------------------------------------------ | ----------------------------------------------------------------- |
| `@typescript-eslint/no-non-null-assertion` | Sometimes the honest answer after an explicit runtime check       |
| `@typescript-eslint/no-deprecated`         | Deprecations need scheduled migration, not immediate blocking     |
| `vitest/no-disabled-tests`                 | A temporarily disabled test is legitimate; a forgotten one is not |

Do not add a rule as `warn` to avoid fixing violations. Either fix them, or change the
rule and justify it in the pull request.

Once the `warn` count reaches zero, consider `eslint . --max-warnings=0` in CI to keep
it there.

## 4. Rule rationale

The rules below are the ones that are opinionated, non-obvious, or specific to QAT.

### Async correctness

`no-floating-promises`, `no-misused-promises`, `await-thenable`, `require-await` —
all `error`.

An un-awaited promise in a CLI means the command finishes before its work does, so the
exit code describes nothing. This is the most dangerous defect class in a tool whose
primary output is an exit code.

### Exit codes

`no-process-exit`: `error`, with the sole exemption of `src/core/process/`.

Exit codes are part of QAT's public contract. Every exit path must go through the
exit-code abstraction so it can be asserted on in a unit test. A raw `process.exit()`
is untestable and bypasses the contract.

### Output

`no-console`: `error`, with exemptions for `src/cli/output/` and `src/core/process/`.

Console output bypasses Pino, which means it loses level filtering, credential
redaction, and structured fields. All user-facing output goes through the output layer.

### Exhaustiveness

`switch-exhaustiveness-check`: `error`.

The result-status and exit-code unions will gain members. A new member falling through
a `switch` without a compile error produces a wrong exit code, which is a false pass.

### Error preservation

`preserve-caught-error`: `error`.

When wrapping an error, keep the original as `cause`. Without it, a diagnostic says
"execution failed" and nothing else, which is precisely the problem QAT exists to solve.

### Type safety at boundaries

`no-explicit-any` and the `no-unsafe-*` family: `error`.

QAT's job is parsing untrusted output from Cypress, JUnit XML and third-party config.
Those boundaries are where types earn their value. Use `unknown` and narrow; do not
assert.

### Imports

`consistent-type-imports` (`separate-type-imports`) and `no-import-type-side-effects`:
`error`. Mandated by `verbatimModuleSyntax` in `tsconfig.json` — a value import of a
type emits a real runtime import of nothing.

`import-x/order`: `error`, autofixable. Do not hand-order imports; run `npm run lint:fix`.

`import-x/no-unresolved` is **off**. Module resolution is enforced by `tsc` under
`moduleResolution: nodenext`, which understands the mandatory `.js` extension on
TypeScript imports. The ESLint resolver does not, so enabling the rule here only
produces false positives.

### Unused code

`no-unused-vars` (TS variant): `error`, with a leading-underscore opt-out.

`_` prefix is the agreed signal for an intentionally unused parameter. `noUnusedLocals`
and `noUnusedParameters` in `tsconfig.json` enforce the same rule at build time; ESLint
is kept as well because its messages are more precise and it supports the `_` escape.

### Tests

`vitest/no-focused-tests`: `error`. A committed `.only` reduces the suite to a single
test while the run still reports success — a false green.

`vitest/expect-expect` and `vitest/valid-expect`: `error`. A test that asserts nothing
passes unconditionally.

Type-safety rules are relaxed for tests: fixtures deliberately construct malformed
input, and strict typing there exercises the compiler rather than the code under test.

## 5. Suppression policy

Suppressions are permitted, but never silent.

```ts
// eslint-disable-next-line @typescript-eslint/no-explicit-any -- third-party
// type from execa is declared as any and cannot be narrowed without a cast.
```

Requirements:

1. **Never** use a file-level `/* eslint-disable */`.
2. Every suppression carries `--` and a reason on the same line.
3. Prefer `eslint-disable-next-line` over block directives.
4. Stale directives are errors. `reportUnusedDisableDirectives: 'error'` fails the build
   once the underlying problem is fixed, so suppress elsewhere instead of accumulating
   dead comments.
5. A suppression that only exists because a rule is wrong is a signal to change the rule
   in a reviewed pull request.

## 6. Formatting decisions

| Setting          | Value      | Reason                                                             |
| ---------------- | ---------- | ------------------------------------------------------------------ |
| `printWidth`     | 100        | TypeScript generics and option objects exceed 80 columns routinely |
| `tabWidth`       | 2          | Consistent with JSON and YAML in the same repository               |
| `useTabs`        | false      | Spaces render identically everywhere                               |
| `semi`           | true       | Avoids ASI failure modes with leading `(` and `[`                  |
| `singleQuote`    | true       | Fewer escapes in TypeScript                                        |
| `trailingComma`  | `all`      | Multi-line additions produce one-line diffs                        |
| `arrowParens`    | `always`   | Removing a parameter does not churn the diff                       |
| `endOfLine`      | `lf`       | Windows and Linux developers share one history                     |
| `proseWrap` (md) | `preserve` | Reflowing prose rewrites whole documents                           |

Formatting is not reviewed. Run `npm run format` and move on; do not hand-wrap code to
fit a width Prettier will change anyway.

## 7. CI

CI runs `npm run verify`, which fails on any lint error or any formatting deviation. A
pull request that fails `format:check` is not reviewed until it is formatted — reviewers
should not spend time on diffs a formatter produced.

## 8. Changing these standards

Rule changes are `chore` commits with a rationale in the body. Removing a rule requires
stating which violations were acceptable and why. Adding a rule requires stating what
defect class it prevents.

Both tools are pinned in `package-lock.json`. Upgrade them in dedicated pull requests so
that a rule change and a dependency change are never mixed in one diff.
