# CLI Commands

|                       |                                                                                                                                    |
| --------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| **Status**            | Normative                                                                                                                          |
| **Registry**          | `src/cli/commands/index.ts`                                                                                                        |
| **Contract**          | `src/cli/contracts.ts` → `CommandDefinition`                                                                                       |
| **Help generated by** | `src/cli/program.ts` → `registerCommand`                                                                                           |
| **Companion**         | [`cli-bootstrap.md`](cli-bootstrap.md), [ADR-0013](../architecture/adr/0013-register-a-command-only-when-its-capability-exists.md) |

How a command is declared, registered, documented and tested.

## 1. The inventory policy

**A command is registered when its capability exists, not when it is planned.**

`qat --help` reads the registry, so the registry is a statement about what the tool _does_ rather than
about what it intends to do. Registering a command whose handler is a stub puts a promise in front of
a user and breaks it on the first invocation, in the order they try things.

The approved inventory names more commands than are registered today. That is expected: the help
screen is short because the tool is short.

| Command                                                | Registered | Because                                                                              |
| ------------------------------------------------------ | ---------- | ------------------------------------------------------------------------------------ |
| `doctor`                                               | Yes        | Discovery, the environment utilities and the error model already answer its question |
| `init`, `run`, `report`, `history`, `diff`, `diagnose` | No         | Their capability does not exist yet                                                  |

A stub is not a placeholder for a future feature; it is a defect that ships.

## 2. The command contract

```ts
export interface CommandDefinition {
  readonly name: string;
  readonly summary: string;
  readonly description: string;
  readonly arguments?: readonly CommandArgument[];
  readonly options?: readonly CommandOption[];
  readonly examples: readonly string[];
  readonly run: (context: CommandContext) => Promise<void>;
}
```

| Field         | Rules                                                                     | Enforced by                     |
| ------------- | ------------------------------------------------------------------------- | ------------------------------- |
| `name`        | Lowercase, one word, unique in the registry                               | Registry test (uniqueness)      |
| `summary`     | One line, no trailing full stop, no line break. Shown in the command list | Registry test                   |
| `description` | Prose, may span lines. Shown in the command's own help                    | Registry test                   |
| `arguments`   | In the order the user supplies them; names unique                         | Registry test                   |
| `options`     | Command-specific only — global options are declared once on the program   | Registry test checks flag shape |
| `examples`    | **At least one**, beginning with `qat <name>`                             | Registry test                   |
| `run`         | Receives a `CommandContext`, returns nothing                              | The compiler                    |

`description` is prose, not a restatement of `summary` and not a list of arguments — those have their
own fields, and repeating them in prose is how the two drift apart.

## 3. Arguments and options

**An argument is what the command is about. An option modifies how it behaves.**

| Use a positional when                                     | Use an option when                                       |
| --------------------------------------------------------- | -------------------------------------------------------- |
| There is one obvious subject: `qat doctor ./packages/api` | The value is a setting: `qat run --suite smoke`          |
| Omitting it has an obvious default                        | Omitting it has a meaningful default the user should see |
| It reads as a sentence                                    | It reads as a flag                                       |

`required` is stated in the definition and the brackets in help are generated from it, so the two
cannot disagree:

```ts
{ name: 'directory', description: 'directory to inspect', required: false }
// → rshown as [directory]
```

An omitted optional argument **is absent from `context.arguments`**, not an empty string. A handler
can therefore distinguish "not provided" from "provided as nothing" — the same distinction the
environment utilities make, for the same reason.

## 4. How help is produced

Nothing is written by hand. An argument the command accepts but does not describe is not expressible,
which removes the usual way help drifts from behaviour.

| What the user sees    | Where it comes from                                     |
| --------------------- | ------------------------------------------------------- |
| Command list entry    | `name` and `summary`                                    |
| `Usage:` line         | `name` plus the argument names and their required flags |
| Argument descriptions | `arguments[].description`                               |
| Option descriptions   | `options[].description` and the global options          |
| Default values        | `defaultValue`, shown as `(default: …)`                 |
| `Examples:` block     | `examples`, appended after the generated help           |

## 5. Where commands live

```
src/cli/commands/
├── index.ts        ← the registry
└── doctor.ts       ← one file per command
```

`index.ts` exports a single `COMMANDS` array. Nothing else in the CLI knows which commands exist;
`createProgram` is handed the array.

## 6. Adding a command

1. **Write the definition** in `src/cli/commands/<name>.ts`. Export a `const` typed as
   `CommandDefinition`.
2. **Use the application, do not build it.** The handler receives `context.application`; reaching for
   `createApplication` would assemble a second one and nothing would notice.
3. **Write output through the output layer.** `reportResult` for a result, and let errors propagate —
   the entry point renders them and decides the exit code.
4. **Add it to `COMMANDS`.**
5. **Add a help test.** The registry test runs over every command, so most of the work is automatic;
   add a specific case only for behaviour unique to the command.
6. **Add end-to-end cases** if the command changes the exit-code surface: success, and each way it can
   fail.

No change to `program.ts` or `index.ts` is required, and none should be needed.

## 7. Worked example

```ts
import { reportResult } from "../output/report.js";
import type { CommandDefinition } from "../contracts.js";

export const doctorCommand: CommandDefinition = {
  name: "doctor",
  summary: "Report what QAT can see about this project",
  description: [
    "Inspects the project in the given directory and reports what was found.",
    "",
    "Intended to be run before the first execution, so an unusual layout or a missing",
    "framework is discovered in a second rather than in the middle of a run.",
  ].join("\n"),
  arguments: [
    {
      name: "directory",
      description:
        "directory to inspect; defaults to --cwd, or to the working directory",
      required: false,
    },
  ],
  examples: ["qat doctor", "qat doctor ./packages/api", "qat doctor --json"],
  async run({ application, arguments: values, options }) {
    const directory = values["directory"] ?? options.cwd ?? process.cwd();
    const project = await application.discovery.discover(directory);

    reportResult(
      {
        lines: [`project    ${project.name}`, `root       ${project.root}`],
        document: { project },
      },
      { json: options.json },
    );
  },
};
```

Three things this example gets right that are easy to get wrong: it names a precedence for the
directory rather than leaving two sources to fight, it wraps the machine-readable output in an object
so a field can be added later, and it lets a discovery failure propagate rather than catching it and
inventing an exit code.

## 8. Testing a command

| Level      | Where                              | What it must prove                                                                                                     |
| ---------- | ---------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| Registry   | `tests/unit/cli/help.test.ts`      | Summary, description, examples and unique names — automatically, for every command                                     |
| Program    | `tests/unit/cli/program.test.ts`   | Registration mechanics: arguments passed by name, an omitted one absent, an extra one rejected, disposal on both paths |
| Command    | `tests/unit/cli/<command>.test.ts` | The handler's own logic, with a fake application                                                                       |
| End-to-end | `tests/e2e/cli.test.ts`            | The built binary, real exit codes, real streams                                                                        |

A command handler is a function taking a context, so testing it needs no process. The end-to-end cases
exist for the things a unit test cannot see: the exit code, the stream, and whether the compiled
output runs at all.

## 9. Global options and command options

Global options are declared once on the program and are available to every command through
`context.options`:

| Flag                  | Purpose                                       |
| --------------------- | --------------------------------------------- |
| `--cwd <directory>`   | Run as if started in this directory           |
| `--log-level <level>` | Diagnostic verbosity                          |
| `--json`              | Machine-readable output                       |
| `--debug`             | Include developer diagnostics in error output |

**A command must not redeclare one.** Two commands with subtly different `--json` behaviour is the
outcome, and only one of them is right.

Command-specific options go in `options`, and the parser defaults them, so `context.commandOptions`
already has the value the handler should use.

## 10. Changing or removing a command

Renaming an argument or a flag is a **user-visible breaking change**: scripts call these. It needs a
`BREAKING CHANGE` footer, a mention in `CHANGELOG.md`, and — while the tool is pre-1.0 — is still
worth avoiding rather than doing twice.

Removing a command is the same, plus a check of the inventory: if it was registered, its capability
existed, so removing it means the capability went too, and that is a decision rather than a cleanup.

## 11. Not here yet

| Item                                             | Trigger                                                                                                                 |
| ------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------- |
| Command-specific options on a registered command | The first command that needs one. The mechanism passes `options` through and Commander declares them; `doctor` has none |
| Subcommand groups (`qat env add`)                | A family of commands that share a noun                                                                                  |
| Deprecation warnings                             | A command that must stay for compatibility                                                                              |
| Shell completion                                 | A user asking for it                                                                                                    |

## 12. Things that will bite

**An example that does not begin with the command name is a failed test, not a documentation
nicety.** The registry asserts the shape, because an example missing the command teaches something
that does not run.

**`context.arguments` is populated at action time.** `command.args` is empty during registration.
Hoisting the read out of the handler will break in a way that looks like argument passing being
broken.

**`allowExcessArguments(false)` is set per command.** Without it, a surplus word is silently ignored
and the user retries into the same result.

**A command that writes to standard output directly bypasses `--json`.** Results go through
`reportResult`, which honours the flag; a `process.stdout.write` in a handler does not.
