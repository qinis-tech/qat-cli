How a command is declared, registered, documented and tested.

## 1. The inventory policy

**A command is registered when its capability exists, not when it is planned.**

`qat --help` reads the registry, so the registry is a statement about what the tool _does_ rather than about what it
intends to do. Registering a command whose handler is a stub puts a promise in front of a user and breaks it on the
first invocation, in the order they try things.

The approved inventory names more commands than are registered today. That is expected: the help screen is short
because the tool is short.

| Command                                                | Registered | Because                                                                                                   |
| ------------------------------------------------------ | ---------- | --------------------------------------------------------------------------------------------------------- |
| `doctor`                                               | Yes        | Detection, diagnosis and validation answer its question, and it reports the answer rather than raising it |
| `init`, `run`, `report`, `history`, `diff`, `diagnose` | No         | Their capability does not exist yet                                                                       |

A stub is not a placeholder for a future feature; it is a defect that ships.

## 2. The command contract

```ts
export interface CommandDefinition {
  readonly name: string;
  readonly summary: string;
  readonly description: string;
  readonly arguments?: readonly CommandArgument[];
  readonly options?: readonly CommandOption[];
  readonly examples: readonly string[];
  readonly run: (context: CommandContext) => Promise<ExitCode | void>;
}
```

| Field         | Rules                                                                     | Enforced by                     |
| ------------- | ------------------------------------------------------------------------- | ------------------------------- |
| `name`        | Lowercase, one word, unique in the registry                               | Registry test (uniqueness)      |
| `summary`     | One line, no trailing full stop, no line break. Shown in the command list | Registry test                   |
| `description` | Prose, may span lines. Shown in the command's own help                    | Registry test                   |
| `arguments`   | In the order the user supplies them; names unique                         | Registry test                   |
| `options`     | Command-specific only — global options are declared once on the program   | Registry test checks flag shape |
| `examples`    | **At least one**, beginning with `qat <name>`                             | Registry test                   |
| `run`         | Receives a `CommandContext`; returns a status or nothing                  | The compiler                    |

`description` is prose, not a restatement of `summary` and not a list of arguments — those have their own fields, and
repeating them in prose is how the two drift apart.

### A command either reports or throws

| Way out              | Means                                                                                   | Who acts on it                                    |
| -------------------- | --------------------------------------------------------------------------------------- | ------------------------------------------------- |
| `throw`              | The command could not do its job: a directory that does not exist, a stream that failed | The entry point renders it and sets the exit code |
| return an `ExitCode` | The command did its job and found something that makes the run a failure                | The action wrapper records it on the process      |

A **reporting** command describes a condition instead of raising it, so it needs a way to say "this failed" without
throwing. That is the whole reason `run` may return a status, and the distinction from §1 of
[cli-output.md](cli-output.md) applies: a _failure_ is an exception, a _finding_ is part of the answer.

`void` in the union is load-bearing. `Promise<void>` satisfies `Promise<ExitCode | void>` and does **not** satisfy
`Promise<ExitCode | undefined>`, so a handler with nothing to declare keeps compiling. Tidying it to `undefined`
breaks every such handler with an error that points at the contract rather than at the tidy-up.

A command never sets `process.exitCode` itself. The action wrapper in `program.ts` does, once, after the handler has
returned and the application has been disposed.

## 3. Arguments and options

**An argument is what the command is about. An option modifies how it behaves.**

| Use a positional when                                     | Use an option when                                       |
| --------------------------------------------------------- | -------------------------------------------------------- |
| There is one obvious subject: `qat doctor ./packages/api` | The value is a setting: `qat run --suite smoke`          |
| Omitting it has an obvious default                        | Omitting it has a meaningful default the user should see |
| It reads as a sentence                                    | It reads as a flag                                       |

`required` is stated in the definition and the brackets in help are generated from it, so the two cannot disagree:

```ts
{ name: 'directory', description: 'directory to inspect', required: false }
// → shown as [directory]
```

An omitted optional argument **is absent from `context.arguments`**, not an empty string. A handler can therefore
distinguish "not provided" from "provided as nothing" — the same distinction the environment utilities make, for the
same reason.

**A command does not resolve its own directory.** `context.application.discovery.resolveWorkingDirectory` owns the
precedence between a positional, `--cwd` and the process directory, and it validates the result. A handler that writes
`values['directory'] ?? options.cwd ?? process.cwd()` re-derives that rule, and will eventually derive it differently
from its neighbour — which is a bad argument reaching a service instead of a usage error.

## 4. How help is produced

Nothing is written by hand. An argument the command accepts but does not describe is not expressible, which removes the
usual way help drifts from behaviour.

| What the user sees    | Where it comes from                                     |
| --------------------- | ------------------------------------------------------- |
| Command list entry    | `name` and `summary`                                    |
| `Usage:` line         | `name` plus the argument names and their required flags |
| Argument descriptions | `arguments[].description`                               |
| Option descriptions   | `options[].description` and the global options          |
| Default values        | `defaultValue`, shown as `(default: …)`                 |
| `Examples:` block     | `examples`, appended after the generated help           |

## 5. Where commands live

```
src/cli/commands/
├── index.ts        ← the registry
└── doctor.ts       ← one file per command
```

`index.ts` exports a single `COMMANDS` array. Nothing else in the CLI knows which commands exist; `createProgram` is
handed the array.

## 6. Adding a command

1. **Write the definition** in `src/cli/commands/<name>.ts`. Export a `const` typed as `CommandDefinition`.
2. **Use the application, do not build it.** The handler receives `context.application`; reaching for
   `createApplication` would assemble a second one and nothing would notice.
3. **Ask a service, do not compute.** One call for the question, and no threshold, filename or rule in the handler.
   `doctor` is four calls: resolve, assess, report, status.
4. **Write output through the output layer.** `reportResult` for a result, `reportLines` to build it. A
   `process.stdout.write` in a handler bypasses `--json` and is a defect.
5. **Decide whether a bad answer is a throw or a status.** A condition the command can _describe_ is a status; a
   condition that stopped it before it could describe anything is a throw.
6. **Add it to `COMMANDS`.**
7. **Add a help test.** The registry test runs over every command, so most of the work is automatic; add a specific
   case only for behaviour unique to the command.
8. **Add end-to-end cases** if the command changes the exit-code surface: success, warnings-only, and each way it can
   be blocked.

No change to `program.ts` or `index.ts` is required, and none should be needed.

## 7. Worked example

The registered `doctor`, shortened to its structure:

```ts
import type { CommandDefinition } from "../contracts.js";
import { exitCodeFor, reportLines, reportResult } from "../output/index.js";

export const doctorCommand: CommandDefinition = {
  name: "doctor",
  summary: "Report what QAT can see about this project",
  description: [
    "Inspects the project in the given directory and reports what was found: the package identity, whether the framework is declared and where its installation came from, the configuration QAT would use, and every condition that would prevent a run.",
    "Each condition is printed with the code it is known by, the file it concerns, and what to do about it. Exits non-zero when a blocking condition is found, having printed it; warnings do not affect the exit status.",
  ].join("\n\n"),
  arguments: [
    {
      name: "directory",
      description:
        "directory to inspect; overrides --cwd, and defaults to the working directory",
      required: false,
    },
  ],
  examples: ["qat doctor", "qat doctor ./packages/api", "qat doctor --json"],
  async run({ application, arguments: values, options }) {
    const { directory } = await application.discovery.resolveWorkingDirectory({
      argument: values["directory"],
      option: options.cwd,
    });

    const assessment = await application.discovery.assess(directory);

    reportResult(
      { lines: reportLines(assessment), document: { assessment } },
      { json: options.json },
    );

    return exitCodeFor(assessment);
  },
};
```

Five things this example gets right that are easy to get wrong:

- **The precedence is delegated.** One resolver, one answer, one place that validates it.
- **The handler computes nothing.** Every line it prints came from the assessment, including the verdict.
- **It reports rather than throws**, and returns the status that makes the report a failure.
- **The document is the contract**, not a presentation of it: a field added to the assessment needs no change here.
- **The presentation is elsewhere.** `reportLines` is a pure function, so the report shape is unit-tested with literal
  strings instead of a stream.

## 8. Testing a command

| Level      | Where                                | What it must prove                                                                                                                                                     |
| ---------- | ------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Registry   | `tests/unit/cli/help.test.ts`        | Summary, description, examples and unique names — automatically, for every command                                                                                     |
| Program    | `tests/unit/cli/program.test.ts`     | Registration mechanics: arguments passed by name, an omitted one absent, an extra one rejected, disposal on both paths, and that a returned status reaches the process |
| Presenter  | `tests/unit/cli/diagnostics.test.ts` | The report shape, spacing and exit-status mapping, from values                                                                                                         |
| End-to-end | `tests/e2e/<command>.test.ts`        | The built binary, real exit codes, real streams, and that nothing was written to the project                                                                           |

The end-to-end suite is **one file per area** rather than one per binary: `doctor`, `executable`, `version`, `help`,
`unknown-input`, `working-directory`. Vitest parallelises across files and serialises within one, so the split is
faster as well as easier to read — and a failure names the area rather than the binary.

`doctor` has no `tests/unit/cli/doctor.test.ts`, and does not need one: its handler is four calls with nothing to
branch on, and the presentation it delegates to carries the unit coverage. A command whose handler _does_ branch should
have one, with a fake application.

## 9. Global options and command options

Global options are declared once on the program and are available to every command through `context.options`:

| Flag                  | Purpose                                       |
| --------------------- | --------------------------------------------- |
| `--cwd <directory>`   | Run as if started in this directory           |
| `--log-level <level>` | Diagnostic verbosity                          |
| `--json`              | Machine-readable output                       |
| `--debug`             | Include developer diagnostics in error output |

**A command must not redeclare one.** Two commands with subtly different `--json` behaviour is the outcome, and only one
of them is right.

Command-specific options go in `options`, and the parser defaults them, so `context.commandOptions` already has the
value the handler should use.

## 10. Changing or removing a command

Renaming an argument or a flag is a **user-visible breaking change**: scripts call these. It needs a
`BREAKING CHANGE` footer, a mention in `CHANGELOG.md`, and — while the tool is pre-1.0 — is still worth avoiding rather
than doing twice.

Changing **what a command writes to which stream** is the same kind of change even when no flag moves. Moving a
condition from standard error to standard output, or the reverse, breaks anything matching on one of them.

Removing a command is the same, plus a check of the inventory: if it was registered, its capability existed, so removing
it means the capability went too, and that is a decision rather than a cleanup.

## 11. Not here yet

| Item                                             | Trigger                                                                                                                       |
| ------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------- |
| Command-specific options on a registered command | The first command that needs one. Commander declares them and `context.commandOptions` passes them through; `doctor` has none |
| The gate that refuses an execution               | The first command that acts. `assertReadyFor` exists and is tested; no command calls it, because no command executes anything |
| Subcommand groups (`qat env add`)                | A family of commands that share a noun                                                                                        |
| Deprecation warnings                             | A command that must stay for compatibility                                                                                    |
| Shell completion                                 | A user asking for it                                                                                                          |

## 12. Things that will bite

**An example that does not begin with the command name is a failed test, not a documentation nicety.** The registry
asserts the shape, because an example missing the command teaches something that does not run.

**`context.arguments` is populated at action time.** `command.args` is empty during registration. Hoisting the read out
of the handler will break in a way that looks like argument passing being broken.

**`allowExcessArguments(false)` is set per command.** Without it, a surplus word is silently ignored and the user
retries into the same result.

**A command that writes to standard output directly bypasses `--json`.** Results go through `reportResult`, which
honours the flag; a `process.stdout.write` in a handler does not.

**A command that throws for a project condition reinstates the behaviour the assessment removed.** The exception
carries a code and a sentence and nothing else; the findings, the remedies and the verdict are lost. If a condition can
be described, it is a result.

**A returned status that nobody applies is invisible.** A handler returning `ExitCode.InvalidInput` while the action
wrapper ignores the value produces a report that says `result blocked` and a process that exits `0`. Nothing in the unit
tests notices; only an end-to-end assertion on `$?` does. That is why §8's program row lists it.
